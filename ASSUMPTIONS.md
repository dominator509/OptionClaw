# OptionClaw Assumptions

| ID | Assumption | Reason | Risk if Wrong | How to Verify | Blocks Implementation |
|---|---|---|---|---|---|
| A-001 | The repository is greenfield and may contain no Rust project files yet. | The input states "Greenfield repository" and package manager/testing are unknown. | Scripts that assume `Cargo.toml` would fail before foundation setup. | Run `ls -la`, check for `Cargo.toml`, `Cargo.lock`, `src/`, and existing CI files during EP-000. | No; EP-001 creates the foundation if missing. |
| A-002 | Rust with Cargo is the default package manager and build system. | Preferred stack says Rust for frontend/CLI and backend. | A non-Cargo Rust workspace or alternative build system would require command updates. | Run `command -v cargo`, inspect existing files for `Cargo.toml`, `justfile`, `Makefile`, or workspace metadata. | Yes if Cargo is unavailable and no equivalent command set is approved. |
| A-003 | Initial user interface is a CLI, not a web app. | Requirements prefer CLI for speed and lean local operation. | Missing user flows if a GUI is later required. | Confirm by reading product docs and current repository routes/UI files during EP-000. | No; CLI contracts are specified. |
| A-004 | No external database is used in the initial architecture. | Preferred stack says "No database". | Durable state may need migration to SQLite/Postgres if audit/query needs grow. | Inspect current code and deployment constraints during EP-000; review performance and retention requirements during EP-003. | No; initial persistence uses local files with schema versions. |
| A-005 | Local encrypted files are acceptable for configuration state, secrets metadata, strategy snapshots, paper-trade state, and audit records. | No database is requested but the product needs restartable operation and auditability. | File locking, corruption handling, or audit query needs could exceed simple file storage. | Implement EP-003 integration tests for crash-safe writes, corruption handling, backup, and restore. | No; can be replaced by a later ExecPlan if needed. |
| A-006 | Live trading must be disabled until paper trading, sandbox integration, risk gates, secret handling, and kill-switch behavior pass tests. | Autonomous trading can cause irreversible financial loss. | Users may expect immediate live trading. | CLI must show live trading as unavailable until explicit configuration and production readiness pass. | Yes for live-order submission only. |
| A-007 | Broker/exchange platform selection is not fixed in the blueprint. | The input asks for most API-supported options platforms, preferably crypto funded, but does not name accounts or jurisdictions. | Implementing against the wrong provider wastes effort or creates compliance risk. | EP-004 must implement provider-agnostic traits first; broker-specific adapters require verified official docs, sandbox credentials, and a separate decision entry. | Yes for broker-specific live integration. |
| A-008 | Wallet connectivity is integration-scoped, not core-domain-scoped. | Wallet operations involve custody and secret/private-key risk. | Premature wallet code could leak keys or fund incorrect accounts. | EP-004 defines wallet adapter contracts; EP-006 defines secret and signing safety. | Yes for real wallet signing or fund movement. |
| A-009 | LLM brain is advisory and must pass deterministic risk gates before any order intent can proceed. | LLMs can hallucinate and are not reliable as sole financial decision makers. | An LLM-only path could submit unsafe orders. | Unit and integration tests must verify risk gates reject unsafe LLM recommendations. | Yes for any order path that bypasses deterministic gates. |
| A-010 | Profitability metrics are simulated/paper-trading metrics during development. | Historical/live performance claims need rigorous validation and cannot be assumed. | Misleading product claims or unsafe behavior. | Backtesting and paper-trading reports must label data source, mode, and limitations. | No for software implementation; yes for marketing claims. |
| A-011 | CI target is GitHub Actions unless repository discovery proves otherwise. | Most greenfield repositories can use GitHub Actions, but CI/CD is unknown. | Wrong CI format if hosted elsewhere. | EP-000 checks `.github/`, `.gitlab-ci.yml`, etc. | No; update COMMANDS.md if different. |
| A-012 | OpenAI-compatible and self-hosted LLM endpoints are both configuration options. | Requirement mentions OpenAI-type APIs or self-hosted LLM. | Specific provider API may differ. | Provider adapters must be contract-tested and configured through explicit environment variables. | No for mock provider; yes for real provider. |
| A-013 | Authentication is not user-login-based for the local CLI. | Single-user local operation is implied. | Multi-user deployments would need identity, roles, and secret isolation. | EP-006 confirms deployment mode and enforces file permissions, config permissions, and command-level confirmation instead. | No for local CLI; yes for multi-user service mode. |
| A-014 | Production means operator-owned local hardware/VPS, not a hosted SaaS. | Deployment target says local hardware and may be Raspberry Pi or VPS. | SaaS requirements for tenancy, billing, and web security would be missing. | EP-009 documents deployment topology and verifies systemd/container options. | No for local deployment. |
| A-015 | Accessibility requirements map to CLI usability: clear output, non-color-only status, readable errors, and keyboard-only operation. | UI is CLI. | Future GUI would need separate accessibility criteria. | EP-005 validates CLI output and terminal behavior. | No. |
| A-016 | Local discovery evidence is authoritative for the initial foundation: this checkout currently has docs and scripts only, no Git worktree, no `Cargo.toml`, and no `src/`, `tests/`, `config/`, or `.github/workflows/` tree yet. | EP-000 inventory and command output. | EP-001 must create the Rust foundation before build/test scripts can work. | Re-run discovery after EP-001 or once a Git checkout is restored. | No; it informs the foundation plan rather than blocking it. |
| A-017 | EP-003 persistence can use schema-versioned local JSON files plus append-only JSONL audit logs without an external database. | SPEC-002 and the persistence plan call for local file state and backups only. | Future retention or query needs could require a database if file storage becomes insufficient. | Validate `init_data_dir`, `verify_data_dir`, `append_audit`, `write_state_atomic`, and backup/restore integration tests. | No; EP-003 implements this storage shape. |
